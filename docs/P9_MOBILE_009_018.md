# SafeContracts P9 — Mobile Operations SC-P9-009..018

## Scope

This delivery turns the capability-aware mobile shell into an operational client for the existing SafeContracts WordPress backend.

| Task | Mobile behavior |
|---|---|
| SC-P9-009 | Generate the current authorized Excel report through `GET /reports/excel`, decode the server workbook and stage it as a local file. |
| SC-P9-010 | Customers list/detail using protected customer REST data. |
| SC-P9-011 | Contracts list using current authorized dashboard filters and bounded sorting/paging. |
| SC-P9-012 | Contract details using safe server projection only. |
| SC-P9-013 | Capability-gated light edits for contract number or the start/end date pair. |
| SC-P9-014 | Payments list using customer/contract/status/due filters and server-authoritative balances. |
| SC-P9-015 | Payment details with contractual Due Date and Expected Payment Date shown separately. |
| SC-P9-016 | Capability-gated Expected Payment Date edit; contractual Due Date is preserved by the backend bridge. |
| SC-P9-017 | Feature/capability-gated collection entry; payment method mandatory and proof optional. |
| SC-P9-018 | Active payment-method lookup from the WordPress reference-data table. |

## Backend mutation boundary

Mobile does not write business tables or recreate financial rules. A restricted REST bridge delegates mutations to the existing domain services:

- `POST /contracts/{id}/light-edit` -> `ContractService`
- `POST /payments/{id}/light-edit` -> `PaymentService`
- `POST /collections` -> `CollectionService`

Permission callbacks require the corresponding WordPress capability, and the domain services continue to enforce assigned/all scope, archived-record restrictions, validation, transaction integrity and audit hooks.

The contract light-edit endpoint deliberately requires contract-number and date-pair changes to be separate requests. This avoids partial multi-operation updates. The payment light-edit endpoint accepts only Expected Payment Date and preserves the stored contractual Due Date.

## Financial authority

Amounts, paid/remaining balances and lifecycle/status values are displayed exactly as returned by WordPress. Flutter does not recalculate settlement, overdue state or contract financial reconciliation.

Collection UX performs only basic input feedback. The backend remains authoritative for money normalization, active payment method validation, scope, over-collection protection, settlement state and audit logging.

## Excel behavior

The server generates the workbook and returns the existing base64 export envelope. Mobile decodes that payload and writes the bytes to the platform temporary directory with a sanitized filename. No spreadsheet is generated on-device. A later platform-sharing task may promote the prepared file into native share/download UX without changing the report authority model.

## Security

- No WordPress password or Application Password is embedded.
- No Firebase service-account/server credential is added to mobile.
- POST requests reuse the existing injected authenticated-header boundary.
- JSON request bodies are capped by the IO transport.
- The REST bridge rejects unknown/non-scalar operation fields.
- Mutation controllers contain no direct SQL.
