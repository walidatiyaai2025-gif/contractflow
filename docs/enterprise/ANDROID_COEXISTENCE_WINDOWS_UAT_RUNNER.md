# ESC Android Coexistence — Windows UAT Operator Runner

## Purpose

`scripts/run_esc_android_coexistence_uat_windows.ps1` is the Windows operator entrypoint for the remaining physical-device coexistence work under #421.

It standardizes the exact-source/device setup and evidence handoff, but it is deliberately not a final UAT decision tool.

The runner:

- reuses `scripts/collect_esc_android_coexistence_uat_session.py` for the already-reviewed objective checks;
- requires one explicit ADB device serial, exact 40-character ESC source SHA, Safe Contract APK, ESC APK and tester identity;
- captures a read-only package/device snapshot for the selected device;
- writes `objective_draft.json`, `device_snapshot.txt`, `manual_evidence_requirements.json` and `runner_summary.json` into a new empty evidence directory;
- leaves the five environment-specific runtime checks pending;
- does not execute application update, data-clear/removal, FCM-send, authentication, backend-session, evidence-bundle or finalization operations;
- never substitutes for the existing content-addressed bundle or the existing finalizer.

The overall runner state is always `PENDING_REAL_DEVICE_UAT`.

## Prerequisites

On the Windows operator workstation:

- repository checkout at the exact ESC source being tested;
- physical Android device with USB debugging enabled and explicitly selected by serial;
- both Safe Contract and ESC already installed on that same device before the runner starts;
- verified Safe Contract production APK;
- ESC production candidate APK built from the exact `enterprise-safecontracts` source SHA;
- Python available as `python` or supplied with `-PythonCommand`;
- Android SDK tools `adb`, `apkanalyzer` and `apksigner` available on PATH or supplied through the command parameters.

The script requires an empty evidence directory and refuses to overwrite previous evidence.

## Run the objective/operator preparation step

From repository root in PowerShell:

```powershell
pwsh -File .\scripts\run_esc_android_coexistence_uat_windows.ps1 `
  -SafeApk 'C:\ESC-UAT\SafeContracts-production.apk' `
  -EscApk 'C:\ESC-UAT\EnterpriseSafeContracts-candidate.apk' `
  -SourceSha '<exact-40-character-esc-source-sha>' `
  -DeviceSerial '<adb-device-serial>' `
  -Tester '<tester-name-or-approved-id>' `
  -EvidenceRoot 'C:\ESC-UAT\evidence\run-001'
```

If the Android SDK commands are not on PATH, provide their executable paths explicitly:

```powershell
  -AdbCommand 'C:\Android\platform-tools\adb.exe' `
  -ApkAnalyzerCommand 'C:\Android\cmdline-tools\latest\bin\apkanalyzer.bat' `
  -ApkSignerCommand 'C:\Android\build-tools\<version>\apksigner.bat'
```

## Generated material

The runner writes only preparation/draft material:

- `objective_draft.json`
  - generated by the existing objective coexistence session collector;
  - remains `decision=PENDING`;
  - contains the objective dual-install, independent-launch and ESC deep-link-isolation observations already supported by that collector.
- `device_snapshot.txt`
  - records source SHA, tester, selected serial, device manufacturer/model/Android version and read-only Safe/ESC package path/version/user/dataDir metadata.
- `manual_evidence_requirements.json`
  - lists the five runtime checks that still require real execution and review;
  - lists the expected evidence artifact handoff names;
  - does not create those artifacts.
- `runner_summary.json`
  - reports objective collection as completed;
  - keeps manual UAT pending;
  - records evidence-bundle and finalization status as `NOT_RUN`.

## Runtime checks that remain manual/environment-specific

The runner does not mark any of these checks complete:

1. `session_isolation`
   - sign in with the approved account for each product;
   - verify each application retains only its own session/tenant context after force-stop/relaunch;
   - retain reviewed screenshots/video/log evidence as `manual/session_isolation.zip`.
2. `safe_only_push`
   - use the approved Safe Contract Firebase/test-notification path;
   - prove only Safe Contract receives/opens the targeted notification;
   - retain reviewed evidence as `manual/safe_only_push.zip`.
3. `esc_only_push`
   - use the approved ESC Firebase/test-notification path;
   - prove only ESC receives/opens the targeted notification;
   - retain reviewed evidence as `manual/esc_only_push.zip`.
4. `independent_update`
   - execute the approved update-lineage scenario for both applications while both remain present;
   - retain before/after version, launch and unaffected-product data evidence as `manual/independent_update.zip`.
5. `clear_data_uninstall_isolation`
   - execute the approved data-lifecycle/removal isolation procedure from `ANDROID_COEXISTENCE_UAT.md`;
   - prove the untouched product remains installed, launchable and data-intact;
   - retain reviewed evidence as `manual/clear_data_uninstall_isolation.zip`.

Do not create an evidence archive merely to satisfy the filename. The file is valid only after that physical-device scenario actually occurred and its contents were reviewed.

## Additional retained evidence required by the bundle

The existing content-addressed bundle also requires:

- `objective_draft` -> `objective_draft.json`;
- `device` -> `device_snapshot.txt`;
- `esc_firebase_identity` -> reviewed ESC Firebase Android app/config evidence;
- `business_uat` -> business-owner UAT sign-off evidence;
- `coexistence` -> reviewed coexistence summary/evidence;
- `firebase_delivery` -> reviewed notification-isolation summary/evidence;
- the five manual runtime artifacts listed above.

`manual_evidence_requirements.json` gives suggested relative artifact names for the operator session. The bundle builder still re-hashes the exact files supplied to it.

## Bundle and finalization handoff

After every required runtime scenario has actually been executed and every retained artifact has been reviewed, use the already-existing tools:

1. `scripts/build_esc_android_coexistence_evidence_bundle.py`
2. `scripts/finalize_esc_android_coexistence_evidence.py`
3. `scripts/validate_esc_android_coexistence_evidence.py`

Those tools remain separate on purpose. The Windows runner does not invoke them and cannot produce the final record.

The finalizer must receive the exact `objective_draft.json` produced for the tested source/device session and the manifest built from the retained evidence root. Source drift, artifact tampering, missing evidence or placeholder references must fail closed under the existing validation path.

## Release boundary

P0-002H improves operator execution and evidence discipline only. It does not close #421.

#421 can close only after the five runtime checks are performed on the physical release candidate, Safe/ESC Firebase and business evidence are retained, the content-addressed bundle is built, and the existing finalizer/validator accepts the exact-source record.
