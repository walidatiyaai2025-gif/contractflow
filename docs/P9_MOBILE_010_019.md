# P9 Mobile implementation — SC-P9-010..019

This slice continues after SC-P9-009 and replaces the authorized Customers, Contracts, Payments and Follow-up placeholders with server-backed workflows. It also adds only the narrow mutation bridges required for contract/payment light edits, collection entry and operational follow-up.

## Tasks

- **SC-P9-010 — Customers screen:** bounded scoped list + protected detail view, refresh/loading/empty/error handling, REST safe fields only.
- **SC-P9-011 — Contracts list:** current authorized dashboard filters, bounded deterministic sort/paging, refresh/loading/empty/error handling.
- **SC-P9-012 — Contract details:** protected direct-object read with server status/base value and explicit API errors.
- **SC-P9-013 — Contract light edits:** `safecontracts_edit_contracts` gated; contract number and paired start/end dates only; `ContractService` remains the domain/audit boundary.
- **SC-P9-014 — Payments list:** current customer/contract/status/due filters, bounded deterministic sort/paging and server-provided balances/status.
- **SC-P9-015 — Payment details:** contractual due date and operational expected date stay separate; original/paid/remaining/status values are displayed exactly as returned by the server.
- **SC-P9-016 — Payment light edits:** `safecontracts_manage_payments` gated expected-payment-date update; the server preserves the contractual due date and delegates to `PaymentService`.
- **SC-P9-017 — Collection entry:** mobile feature flag + capability gate and server operation capability/scope gate; active method required, proof optional; `CollectionService` remains authoritative for financial validation/reconciliation/audit.
- **SC-P9-018 — Payment-method lookup:** active methods come from protected `/reference-data`; mobile never hardcodes the backend master list as authority.
- **SC-P9-019 — Follow-up workflow:** scoped queue/history plus capability-gated note, promise, issue, defer and escalation actions delegated to `FollowUpService`; no mobile mutation of payment status/balances.

## Narrow REST mutation boundary

| Method | Route | Capability | Domain boundary |
|---|---|---|---|
| PATCH | `/contracts/{id}/light` | `safecontracts_edit_contracts` | `ContractService` |
| PATCH | `/payments/{id}/expected-date` | `safecontracts_manage_payments` | `PaymentService` |
| POST | `/collections/record` | `safecontracts_manage_collections` | `CollectionService` |
| POST | `/payments/{payment_id}/followups/record` | `safecontracts_manage_followups` | `FollowUpService` |

All routes also require normal SafeContracts access + VIEW_ALL/VIEW_ASSIGNED scope. Callbacks recheck the operation capability internally, unknown JSON fields fail closed, route identifiers remain authoritative, and the mutation controller contains no direct SQL or independent financial/status reconciliation logic.

## Mobile transport

`SafeContractsApiClient` and the injectable transport gain JSON `POST`/`PATCH` support. Existing session headers, timeout and response-size limits are preserved. Request bodies are JSON encoded only for mutation calls; no second credential/session store is introduced.
