# P9 Mobile implementation — SC-P9-013..019

This slice continues from the merged SC-P9-010 customer, SC-P9-011 contract-list and SC-P9-012 contract-detail work. It adds the remaining mobile business workflows without duplicating those team modules.

## Implemented tasks

- **SC-P9-013 — Contract light edits:** capability-gated edit screen for contract number and paired start/end dates only. Client distinguishes validation (422), forbidden (403), conflict (409) and transport/server failures. Backend delegates to `ContractService`; financial/status/customer/assignment fields are not accepted.
- **SC-P9-014 — Payments list:** protected server-backed payments list using the current customer/contract/status/due filters, deterministic `due_date asc` ordering, bounded paging, refresh/loading/empty/error states and detail navigation.
- **SC-P9-015 — Payment details:** protected direct read with contractual due date kept separate from expected payment date. Original/paid/remaining/status are displayed exactly as returned by the server; no mobile financial recomputation.
- **SC-P9-016 — Payment light edits:** capability-gated expected-payment-date mutation only. The server reuses the existing contractual due date and delegates to `PaymentService`.
- **SC-P9-017 — Collection entry:** feature-flag + capability-gated entry from payment detail. Client validates UX shape only; server scope, remaining-balance rules, reconciliation and audit remain authoritative.
- **SC-P9-018 — Payment-method lookup:** protected `/reference-data` lookup of active server payment methods, including explicit loading/empty/error/retry states. The mobile app does not hardcode the backend master list.
- **SC-P9-019 — Follow-up workflow:** protected queue/history plus capability-gated note, promise, issue, defer and escalation operations through `FollowUpService`. Promise/deferred dates remain operational; mobile never mutates payment balances/status directly.

## Narrow mutation routes

| Method | Route | Capability | Server authority |
|---|---|---|---|
| PATCH | `/contracts/{id}/light` | `safecontracts_edit_contracts` | `ContractService` |
| PATCH | `/payments/{id}/expected-date` | `safecontracts_manage_payments` | `PaymentService` |
| POST | `/collections/record` | `safecontracts_manage_collections` | `CollectionService` |
| POST | `/payments/{payment_id}/followups/record` | `safecontracts_manage_followups` | `FollowUpService` |

Every route also requires the normal SafeContracts access/scope boundary. Unknown JSON fields fail closed, route IDs remain authoritative, callbacks recheck operation capabilities, and the REST mutation controller contains no direct SQL or independent balance/status logic. Archived-domain mutation conflicts are surfaced as HTTP 409; missing scope/capability remains HTTP 403 and input validation remains HTTP 422.
