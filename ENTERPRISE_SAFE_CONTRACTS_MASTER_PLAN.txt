ENTERPRISE SAFE CONTRACTS (ESC) — MASTER PLAN
==============================================

OFFICIAL PRODUCT URL
--------------------
https://esc.50sols.com/

CRITICAL PRODUCT SEPARATION RULE
--------------------------------
Safe Contract = the existing client-specific/current product.
Enterprise Safe Contracts (ESC) = a separate multi-tenant enterprise/SaaS Contract Lifecycle Management product developed on the enterprise-safecontracts branch.

NEVER implement, merge, port, copy, expose, or backport ESC functionality into Safe Contract unless the product owner explicitly requests that exact transfer.
NEVER treat Safe Contract and ESC as the same product, release line, APK, plugin artifact, Firebase app, environment, task stream, or deployment target.

Branch rules:
- Safe Contract/client work: main and client-specific branches/tasks.
- ESC work: enterprise-safecontracts and ESC-* task IDs.
- No PR from enterprise-safecontracts to main merely to "keep branches synchronized".
- Any deliberate transfer between products requires explicit owner instruction, impact analysis, tests, and a bounded PR.

ARCHITECTURAL BASELINE
----------------------
ESC evolves the current architecture rather than discarding it:
- WordPress + custom plugin remain the authoritative backend/business source of truth.
- Flutter remains an API client; financial calculations, authorization and tenant isolation stay server-side.
- Schema changes remain versioned migrations.
- REST APIs remain versioned.
- Security, release provenance, CI and verified-artifact discipline remain mandatory.

PRODUCT GOAL
------------
Build a configurable multi-tenant Contract Lifecycle Management platform usable across many industries without forking the codebase per customer or contract type.

DATA / TENANCY PRINCIPLES
-------------------------
Do not scatter ad-hoc TenantId checks throughout the codebase. Establish Tenant, TenantContext/TenantResolver and tenant-aware repositories/services first, then migrate data domains in controlled stages.
All tenant-owned records must have server-enforced tenant scoping. Object IDs are never authorization.
Cross-tenant access attempts through REST IDs, filters, exports, attachments, mobile requests and background jobs must be explicitly tested.
Start with a shared-database/tenant-key model if selected by ADR, designed so large enterprise tenants may later support stronger isolation/dedicated databases without rewriting the domain.

GENERIC CONTRACT MODEL
----------------------
Avoid one database/domain implementation per industry. Prefer a generic contract core plus ContractType, Template, CustomField, Party, Workflow, Approval, Obligation, Milestone and Financial components.
Industry behavior should primarily be configuration/templates, with code extensions only where genuine domain logic requires them.
